## What you will configure and validate

You'll configure and validate both failure and success cases:

- TO-DO

You'll run the User Context service in a Docker container and launch CCA Realms on an Arm Fixed Virtual Platform (FVP) in a separate Docker container.

You'll use two terminals:

- In the User Context terminal, you'll run the User Context service. This service represents the Realm initiator and decides whether to release BootSync data.
- In the FVP terminal, you'll run the Arm CCA FVP and launch Realm virtual machines using `lkvm-bootsync`.

## Install dependencies

Set up Docker's `apt` repository so you can pull and run the pre-built containers:

```bash
# Add Docker's official GPG key:
sudo apt-get update
sudo apt-get install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Add the repository to APT sources:
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
```

Install Docker packages for the runtime used by both the User Context and FVP containers, and optionally install `git` for inspecting linked source files:

```bash
sudo apt-get install -y git docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Add your user name to the Docker group so you can run Docker without `sudo`:

```bash
sudo usermod -aG docker $USER
newgrp docker
```
The group change applies to new shells; `newgrp docker` updates the current shell.

## Start the User Context service

In the User Context terminal, pull the Docker image with the pre-built User Context service. Then, run the container:

```bash
docker pull anta5010/cca-learning-path:cca-key-broker-v5
docker network create cca-trustee
docker run --rm -it --network cca-trustee --name user-context anta5010/cca-learning-path:cca-key-broker-v5
```

The `cca-trustee` Docker network is important. It lets the FVP container resolve the User Context service by container name, `user-context`, when `lkvm-bootsync` later uses `--service-ip user-context`.

In the User Context terminal, start the User Context service inside the running container using the `run-user-context-service.sh` script.
The User Context service is part of the [EDK2](https://gitlab.arm.com/linux-arm/edk2-cca/-/tree/cca/4441_measured_boot_v1/ArmVirtPkg/ArmCcaBootSync/UserContext) project.
Created specifically as a proof of concept, it's intentionally small and not designed for production use.

When the script starts for the first time, it generates Secure Boot signing certificates and creates a Provisioning Data file.
The Provisioning Data is a binary file generated by [GenPd.py](https://gitlab.arm.com/linux-arm/edk2-cca/-/blob/cca/4441_measured_boot_v1/ArmVirtPkg/ArmCcaBootSync/Scripts/GenPd.py) script.
The file contains EFI variable definitions required for enabling UEFI Secure Boot.

You'll be asked for a passphrase for the Secure Boot signing certificates. Remember it because you'll use it again when signing the Realm kernel.

```bash
./run-user-context-service.sh
```

## Launch Realm with StandaloneMM in Plane0 and Linux in Plane1

With the User Context service running in the User Context terminal, open the FVP terminal.

Pull the Docker image with the pre-built FVP and CCA reference software stack. Then, run the container connected to the same Docker network:

```bash
docker pull anta10/cca-learning-path:cca-simulation-v5
docker run --rm -it --network cca-trustee anta5010/cca-learning-path:cca-simulation-v5
```

Within your running container, launch the `run-cca-fvp.sh` script to run the Arm CCA pre-built binaries on the FVP:

```bash
./run-cca-fvp.sh
```

The `run-cca-fvp.sh` script uses the `screen` command to connect to the different UARTs in the FVP.

When the host Linux boots, log in:

Enter root as the username:
```output

Welcome to the CCA host
host login: root
(host) #
```

Change directory to `/cca` and use `lkvm-planes` to launch a guest Linux in a Realm:

```bash
cd /cca
./lkvm-planes run --realm -m 1G -c 8 --realm-layout plane-map.dtb \
  --irqchip=gicv3-its --nodefaults --force-pci --disk guest-disk.img
```

With this command you start a realm where EDK2 StandaloneMM is launched in Plane0 and Linux kernel is booted by EDK2 UEFI in Plane1.
StandaloneMM includes Secure Variable Storage, (BootSync ???) and vTPM components.


After running the command, you'll see the Realm boot.

## Encrypt the root file system and seal the passphrase with TPM PCR7

You can use vTPM with data provisioned by Arm CCA BootSync to provide access to encrypted file systems.
You'll now encrypt the root file system, seal the passphrase with TPM PCR7 and test how it is used to unlock the disk during boot.

### Encrypt the root partition

In the FVP terminal, use the `encrypt_rootfs.sh` script to encrypt the root partition in the Realm disk image and add an `initrd` image to the kernel parameters.

You'll be asked for a passphrase to encrypt the root partition. Use a memorable test passphrase and keep it available,
because you'll later will be asked for it (or write the same value into `ARMCCA01_SEC.dat` for BootSync to release ???).

You can use a maximum of 512 characters of uppercase or lowercase letters, numbers, and symbols.
Ignore the warning message because you're using small partitions.

### Seal the passphrase with TPM PCR7

At this step you would seal the passphrase and store it in vTPM persisent storage.
Later the data can be used to unlock encrypted file system.

In the FVP terminal, relaunch the Realm.

```bash
cd /cca
./lkvm-planes run --realm -m 1G -c 8 --realm-layout plane-map.dtb \
  --irqchip=gicv3-its --nodefaults --force-pci --disk guest-disk.img
```

In the Realm boot log, you can see that the init script seals the passphrase.
You will be asked for it (if it's not avaliable as a CoCo secrete provisioned by Arm CCA BootSync ???):


The Realm will be stopped after the sealing the passphrase and storing it into vTMP NVRAM.
While the Realm being stopped Arm CCA BootSync will provision the vTPM data to the User Context Service.

### Unlock encrypted file system with the sealed passphrase

Now, when we have vTPM data with the sealed passphrase avaliable we can relaunch the Realm and see how the vTPM is used to unlock encrypted file system.
During Plane1 boot UEFI would execute CCA attestation and if successful vTPM will be provisioned with the data including the sealed passphrase.
It later will be unsealed using PCR7 and used to unlock encrypted file system. The unsealing would be successfull only if PCR7 value would be the same
as it was when the passphrase was sealed. (TO-DO We can also add a falied step. For example when SecureBoot is not set ???)

In the FVP terminal, relaunch the Realm.

```bash
cd /cca
./lkvm-planes run --realm -m 1G -c 8 --realm-layout plane-map.dtb \
  --irqchip=gicv3-its --nodefaults --force-pci --disk guest-disk.img
```

In the Realm boot log, you can see that the init script unseals the passphrase and unlocks the encrypted file system:

``` output
[   40.109947] Run /init as init process
/dev/vda2 is a LUKS paritition.
NVRAM handle 0x81000001 found.
Attempting to unseal LUKS passphrase and unlock /dev/vda2
TPM NVRAM hardware unlock successful, switching root
```

After the Realm boots, log in using `root` as the username:

```output

```
